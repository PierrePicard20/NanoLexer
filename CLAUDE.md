# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

NanoLexer is a C++17 library that generates small, human-readable C++ lexers from regular expressions. Users write a small "generator" program against `NanoLexer::LexerGenerator` (`include/NanoLexer.h`), which emits a header-only lexer template class (e.g. `ArithmeticLexer.h`). The generated header has no dependency on the library.

Primary target is MSVC on Windows; GCC/Clang support is not finished (sources use backslash includes like `<gtest\gtest.h>` and Windows-specific paths).

## Build & test

Requires CMake, Flex and Bison (gnuwin32 packages work on Windows). GoogleTest only when `PACKAGE_TESTS=ON`; with `USE_VCPKG=ON` and `VCPKG_ROOT` set, the vcpkg toolchain is used to find it.

```bash
# library only
cmake -B build -DCMAKE_INSTALL_PREFIX=/path/to/install
cmake --build build --config release
cmake --install build

# with tests
cmake -B build -DUSE_VCPKG=ON -DPACKAGE_TESTS=ON
cmake --build build
ctest --test-dir build                      # add -C Debug/Release for multi-config generators

# single test / suite: run the gtest binary directly
<path-to>/tests.exe --gtest_filter=CppLexerTest.TestBacktrack
<path-to>/tests.exe --gtest_filter=LexerFixture.*
```

All tests are compiled into one executable `tests` (registered with CTest as a single test). New test files must be added to `SRCS` in `tests/CMakeLists.txt`.

The build dir must be `<repo>/build` (or any dir exactly one level below the repo root): `NanoLexer.y` includes `../../NanoLexer/LexerTreeNode.h` relative to the generated parser in `<build>/NanoLexer/`.

The `example/` directory is a standalone consumer project (`find_package(NanoLexer)`), built separately against an installed NanoLexer with `-DCMAKE_PREFIX_PATH=...`.

## Architecture

**Pipeline** (all inside the static library `NanoLexer/`):

1. `NanoLexer.cpp` — implements the public `LexerGenerator` API: collects macros, expressions and contexts, drives parsing and DFA construction, then fills `$(...)` substitution variables and writes output files.
2. `NanoLexer.l` / `NanoLexer.y` — Flex/Bison grammar for the regex syntax itself. Bison/Flex run at build time and produce `NanoLexerParser.cpp`, `NanoLexerLexer.cpp`, `tokens.h` in the build dir (never edit those; edit the `.l`/`.y`). The parser builds a syntax tree using globals (`stackNodes`, `stackSet`, `mapTree`, `errorMessages`); `shared.h` declares what is shared between parser and the rest.
3. `LexerTreeNode.{h,cpp}` (namespace `RegularExpression`) — regex syntax tree (`ConcatNode`, `OrNode`, `StarNode`, `LeafNode`, `RangeNode`, `ExceptNode`, `EndNode`, ...) and character-set algebra (`Set`, `Interval`, `MultiInterval`, `MultiAntiInterval`, `EmptySet`, `WholeSet`). Uses the followpos/position-set construction (`PositionSet`) to go directly from regex to DFA.
4. `LexerBuilder.{h,cpp}` — `State` / `LexerContext`: builds the DFA per context and emits the C++ state-machine code (switch + `goto stateN`) plus the debug string used by tests.

**Contexts**: a lexer can have several contexts (`newContext`, `setPushContext`, `setPopAction`). Non-main contexts become separate methods in the generated class (needed for things like C multiline comments and strings).

**Skeleton templates**: `lexer_sk/<language>/` (only `cpp/Lexer.h` today) contains template files with placeholders such as `$(LexerName)`, `$(LexemeNames)`, `$(LexerContextsMethods)`, `$(OnCreate)`, `$(PublicMembers)`. `generateFiles(language, outputPath)` looks up `lexer_sk/` **next to the running executable** and writes `<LexerName><skeleton filename>` to a path **relative to the executable's directory**. That's why every executable target that generates lexers has a POST_BUILD step copying `lexer_sk/` beside it; the installed package exposes `NanoLexer_LEXER_SK_DIR` for consumers.

## Tests

Two kinds of tests in `tests/`:

- **DFA-structure tests** (`LexerTestCase.cpp`, `CharSetExprTestCase.cpp`, via `LexerFixture`): build a `LexerGenerator` in-process and compare `getDebugString()` to an expected textual dump of states (`s0:'a'->s1;...else->accept N;`). Expression ids are 1-based in order of addition. Set-algebra tests (`IntervalTestCase`, `MultiIntervalTestCase`, `MultiAntiIntervalTestCase`) include `NanoLexer/LexerTreeNode.h` directly.
- **Generated-lexer tests** (`CppLexerTestCase`, `ArithmeticLexerTestCase`, `CommentLexerTestCase`, `SimpleLexer1TestCase`): include headers generated by `testgen/`. The `testgen` executable defines the lexers (one `gen*Lexer()` per file in `testgen/`) and takes the output directory as its only argument. `tests/CMakeLists.txt` runs it through an `add_custom_command(OUTPUT ...)` that writes to `<build>/tests/generated/` and reruns only when `testgen` or `lexer_sk/cpp/*` change. Adding a new generated lexer means adding its header to `GEN_HEADERS` there. To change a generated lexer, edit its `testgen/*.cpp` definition, not the generated header. Use `checkLexemes<Lexer, Lexeme>(text, expected)` from `checkLexemes.h` to assert token sequences.
